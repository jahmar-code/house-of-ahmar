# Backend, security, and data integrity audit — 2026-10-03

## Scope and product boundary

House of Ahmar is one private family House. The database is the tenancy boundary. Supabase email authentication establishes an identity; an active `members` row establishes access to family content; current database role and ownership control mutations. Public signup alone must never grant House membership.

Reviewed the backend-engineer, database-engineer, security-pentester, and software-architect personas, `CLAUDE.md`, all server actions, authentication callback/proxy, database schema/migrations, validators, Storage, and Council data access. Applied the Supabase skill and current primary documentation on [private buckets](https://supabase.com/docs/guides/storage/buckets/fundamentals), [Storage access control](https://supabase.com/docs/guides/storage/security/access-control), and [asset delivery](https://supabase.com/docs/guides/storage/serving/downloads).

## Database evidence and safe rollout

Initial live inspection was read-only and printed schema/policy definitions and aggregate counts only. It found 6 members, 2 active Elders, no Storage objects, and no all-day gatherings. `posts.milestone_kind`, integrity CHECKs, and the expected auth/reply foreign keys were absent. The realtime publication already contained `messages` and `channels`.

Canonical fresh setup is now the migration chain in order: `0001`, `0002`, `0003`, `0004`, `20261003175118_security_and_private_media`. No Drizzle push is required first. `0001` is a non-idempotent historical baseline: **do not replay it over an existing schema**. Existing schema-first deployments apply `0002`, `0003`, `0004`, then the timestamped migration after backup and review.

The new migration preserves object bytes and replaces stored legacy public bucket URLs with `/api/media/...` references. Deploy matching media-route code before or together with the private-bucket change. Public landing pages omit private cover images; externally configured HTTPS covers remain intentionally public. Root owns application-code push/deployment and final release recording in the main audit report.

Root completed a database backup at `backups/2026-10-03T17-55-17/database.sql` before applying the live security migrations. This specialist independently rechecked the live target in a read-only transaction afterward: **14/14 RLS-enabled tables, zero public/anonymous/authenticated write grants, all 3 buckets private with size limits, all 4 private authorization helpers present, and the same 6 members / 2 active Elders**. No family content was printed.

## Remaining operational boundaries

- The existing rate limiter is per-process memory. It limits casual per-account invite mistakes; it is not a shared, distributed abuse-control store. High-entropy codes and atomic redemption are the primary invite protections. Add a durable shared limiter if abuse appears or deployment scales out materially.
- Audit logging is best-effort; mutations remain available when the audit sink fails. This is not a tamper-proof compliance journal.
- Current membership is checked at request time. A relative can retain a previously downloaded image or screenshot; application access revocation cannot recall copies already obtained.
- The database owner connection bypasses RLS by design. New server mutations still require explicit database-backed role/ownership checks, and deployment credentials must remain server-only.
- Root applied the live database migration after its backup. Application code push/deployment is a separate release step; database posture alone does not prove the new media route and UI are deployed.
